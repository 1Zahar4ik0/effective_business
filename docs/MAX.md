## Реализовано

`POST /api/auth/max` получает исходный initData. На сервере выполняется одно URL-декодирование, отклоняются повторяющиеся ключи, вычисляется ключ HMAC от токена с `WebAppData`, проверяются подпись и auth_date. Проект использует более строгий срок 10 минут (допуск будущего 30 секунд); это собственная политика, а не обещание платформы. Хеш запуска сохраняется для защиты от повторного входа. Пользователь определяется только по подписанным данным. Редактор назначается по MAX_ADMIN_IDS. Сессия — случайная HttpOnly cookie, в production Secure, SameSite=None (для встраивания в веб-MAX); изменения требуют CSRF и проверки Origin.

Webhook сравнивает секрет, сохраняет событие в PostgreSQL и быстро возвращает 200. Для message_created ключ дедупликации строится по mid; для остальных событий — по нормализованному содержимому. Поддержаны bot_started, /start, /help, «поддержка». Ответ содержит ссылку MAX_APP_URL. Никаких незапрошенных рассылок.

Очередь `app.jobs` блокирует записи через SKIP LOCKED, ограничивает повторные попытки пятью, использует паузы с увеличением интервала. Повторный webhook не создаёт второй ответ. При сетевой неопределённости после принятия сообщения MAX возможна повторная доставка: гарантия exactly-once для внешнего API не заявляется.

## Что требуется для реального подключения

1. Зарегистрировать бота и мини-приложение на платформе MAX. Назначить отдельный HTTPS-домен приложения.
2. Создать отдельную рабочую БД, использовать APP_ENV=production и SEED_DEMO=false, сильный пароль PostgreSQL и защищённое хранилище токена. Не использовать демонстрационный том.
3. Установить PUBLIC_ORIGIN, MAX_BOT_TOKEN, MAX_WEBHOOK_SECRET, MAX_ADMIN_IDS и MAX_APP_URL (`https://max.ru/<имя_бота>?startapp=...` согласно настройкам бота).
4. Разместить приложение за HTTPS proxy с ограничением частоты запросов и размера тела; разрешить корректную цепочку сертификатов. При необходимости добавить CA bundle, не выключая TLS verification.
5. Зарегистрировать `/api/max/webhook` через официальный POST /subscriptions с secret. Регистрация не выполняется автоматически, чтобы локальный запуск не менял внешние подписки.
6. Запустить очередь: `docker compose -f compose.yaml -f compose.max.yaml up -d` в подготовленном окружении.
7. Пройти полный сценарий в Android/iOS и веб-MAX: launch, повторный вход, навигация, сохранение, внешний переход; проверить доставку webhook и ответов.

Локальные тесты подписи и очереди используют синтетические события. Реальные запросы и сообщения MAX не отправлялись. На текущем компьютере бот не подключён; токен для дальнейшей локальной разработки не нужен.

## Повторная проверка 18.09.2026 — реальные ограничения

Официальные страницы валидации, GET /me и POST /subscriptions прочитаны повторно. Webhook требует **443**, доверенный сертификат и полную цепочку; самоподписанный сертификат не принимается. Подпись — HMAC-SHA256 с ключом WebAppData, токен только в Authorization. Документация: [GET /me](https://dev.max.ru/docs-api/methods/GET/me), [требования webhook](https://dev.max.ru/docs-api/methods/POST/subscriptions).

Локальная диагностика `backend/max_preflight.py` показала отсутствие токена, секрета webhook, ссылки мини-приложения, редакторских ID и HTTPS-origin. Она при наличии токена выполняет только GET /me и GET /subscriptions, проверяет целевой endpoint, не регистрирует подписку, не отправляет сообщения и не выводит тела ответов или секреты. Неизвестный API-origin блокирует передачу токена. Проверка с имитацией ответов — автоматический тест, **не реальная интеграция**.

Безопасное действие пользователя: записать MAX_BOT_TOKEN локально в игнорируемый `.env` для диагностики и сообщить только «токен настроен». Для настоящего входа использовать отдельное production-окружение и `.env.production` по docs/DEPLOYMENT.md. Не присылать токен, initData, cookie или пароль в чат. После установки токена перезапустить контейнер, если диагностика выполняется внутри него: Compose передаёт окружение при создании контейнера.

Проверка из корня: `.venv/Scripts/python.exe backend/max_preflight.py` или `docker compose exec -T app python backend/max_preflight.py`. Для production использовать отдельный compose.production.yaml с `.env.production`. Код завершения 2 означает ненастроенный/недоступный MAX; результат не содержит значений секретов.

Реальный веб-MAX **не проверен**: нет настроенного бота, адреса мини-приложения, публичного HTTPS и токена. Браузерная проверка локального редактора не заменяет этот этап. SameSite=None/Secure устраняет ограничение Lax во вложенном контексте; блокировка сторонних cookies конкретным браузером остаётся предметом реального теста. При таком ограничении не переносить токен сессии в URL или журнал; нужна отдельная согласованная схема хранения сессии.

## Короткая проверка на телефоне после подключения

1. Открыть настроенного бота в **приложении MAX**, нажать кнопку запуска мини-приложения. В рабочем режиме не должно быть кнопок учебного входа.
2. Заполнить неперсональную тестовую анкету. Сохранить, закрыть мини-приложение и открыть заново — ответы должны сохраниться.
3. Проверить подбор: у неполных ответов UNKNOWN, у подтверждённого несоответствия FAIL; завершённый отбор не должен называться открытым.
4. Сохранить план опубликованной проверенной меры, отметить документ и повторно открыть приложение — отметка сохраняется.
5. Нажать официальный маршрут; проверить адрес и шифр. **Не отправлять и не подписывать заявку** при тесте навигатора.
6. Вторым тестовым аккаунтом проверить отсутствие доступа к первому профилю/плану; обычному пользователю недоступен редактор. Повторить в web.max.ru.

Зафиксировать ОС телефона, версию MAX, браузер веб-MAX, время и результаты. Не прикладывать initData/cookie/токены. Проверка подменённой подписи, срока, повторного запуска и прав выполняется автоматическими серверными тестами; окончательная проверка реального запуска возможна только после настройки платформы.

## Проверка перед сдачей

18.09.2026 повторно прочитаны [валидация](https://dev.max.ru/docs/webapps/validation), [Bridge](https://dev.max.ru/docs/webapps/bridge), [webhook](https://dev.max.ru/docs-api/methods/POST/subscriptions) и [история изменений API](https://dev.max.ru/docs-api/changelog-api). В истории указан переход на platform-api2.max.ru и требование доверенного сертификата Минцифры. Настоящий TLS-вызов MAX без токена не заявляется. Политика проекта ограничивает launch data 10 минутами (строже рекомендованного в Bridge часа), разрешает 30 секунд расхождения часов.

Для Docker production добавлен `compose.max-ca.yaml`: он монтирует полный проверенный CA bundle в app и worker. После выбора сервера и получения разрешения на размещение указать `MAX_CA_BUNDLE_HOST` с абсолютным путём в закрытом файле окружения и добавить `-f compose.max-ca.yaml` к команде production Compose. Bundle должен содержать необходимую доверенную цепочку; это не приватный ключ и не самоподписанный тестовый сертификат из tmp. Конфигурация дополнения проверена `config --quiet`; реальное соединение ещё не проверено. Не использовать verify=False.

Текущий отчёт по устройствам: [MAX-DEVICE-REPORT.md](MAX-DEVICE-REPORT.md). Данные от пользователя не получены, успешный мобильный тест не приписывается. Автоматические тесты проверяют также сохранение MAX-профиля после нового подписанного запуска, недоверие к присланной роли и отзыв редакторского доступа существующей сессии.


## Фактическая проверка 20.09.2026

Токен обнаружен в локальном окружении; пользователь разрешил его передачу только официальному API MAX с хранением локально. GET /me завершился ошибкой TLS. Отдельный запрос TLS без токена установил причину: verify_code=20, unable to get local issuer certificate. Это не проверка действительности токена. Ответы API и секреты не выводились, сообщения и регистрация webhook не выполнялись. Страница сертификатов Госуслуг не загрузилась ни веб-инструментом, ни прямым HTTPS-запросом.

MAX_WEBHOOK_SECRET, MAX_APP_URL, MAX_ADMIN_IDS и HTTPS PUBLIC_ORIGIN ещё не настроены. Для локальной цепочки доверия добавлен compose.local-max-ca.yaml. Клиенты запрещают иной API origin, redirects и прокси из окружения. Браузерная проверка каталога не является проверкой MAX. Точные шаги пользователя — [USER-ACTIONS.md](USER-ACTIONS.md).
