## Конфигурация

`compose.production.yaml` запускается **отдельно**, без объединения с `compose.yaml`: отдельные имя проекта и том БД, APP_ENV=production, SEED_DEMO=false, отсутствует демовход. Наружу выходит только Nginx. Для MAX worker включается профилем `max`. Proxy: TLS 1.2/1.3, HSTS, максимум тела 256 КБ, лимиты API/входа и безопасный access log без query string, cookie и Authorization. Лог доступа Uvicorn отключён. Рабочая cookie HttpOnly/Secure/SameSite=None для встраивания; CSRF и Origin остаются обязательными для изменений.

Образ Nginx 1.30.5-alpine проверен по [официальной странице образа](https://hub.docker.com/_/nginx); загруженный digest: `sha256:a5f2157a0302eb0c5e300415effb63a9e70ed1eb9c107283819bf6d149ab607c`. Правила ограничения запросов — [документация Nginx](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html).

После выбора и отдельного разрешения на публикацию:

1. Создать сервер/домен у выбранного провайдера; A-запись домена направить на IPv4. Передать доступ через настроенный SSH-ключ, не сообщением с паролем.
2. Разместить исходники в отдельном каталоге сервера. Создать `.env.production` по `deploy/production.env.example`, ограничить доступ владельцем. Сгенерировать случайный URL-safe пароль PostgreSQL, заполнить DOMAIN, TLS_DIR и настройки MAX. Не выполнять `docker compose config` без `--quiet` в публичном журнале: он раскрывает значения окружения.
3. Получить доверенный TLS-сертификат с полной цепочкой для домена через ACME/провайдера. В `TLS_DIR` разместить обычные файлы `fullchain.pem` и `privkey.pem` с ограниченными правами. Не монтировать только символьные ссылки Certbot без их целей. Процедура выдачи/обновления зависит от выбранного DNS-провайдера; она пока не настроена.
4. Проверить конфигурацию и запустить (команды ниже подготовлены для будущего сервера, удалённый запуск не выполнялся):

```sh
docker compose --env-file .env.production -f compose.production.yaml config --quiet
docker compose --env-file .env.production -f compose.production.yaml up -d --build
docker compose --env-file .env.production -f compose.production.yaml exec -T app python backend/import_official.py --apply
docker compose --env-file .env.production -f compose.production.yaml exec -T proxy nginx -t
```

5. Проверить доверенный HTTPS с внешней сети, пустой публичный каталог до редакторской публикации и отсутствие демовхода. После настройки MAX выполнить `python backend/max_preflight.py` в контейнере и отдельную регистрацию webhook по docs/MAX.md.
6. Включить worker: `docker compose --env-file .env.production -f compose.production.yaml --profile max up -d worker`. Остановка без удаления данных: тот же Compose с `stop`; повторный запуск — `up -d`.

При обновлении сертификата переписать файлы в TLS_DIR, затем `exec -T proxy nginx -s reload`. До реальной сдачи обязателен проверенный автоматический renewal и мониторинг срока сертификата. Самоподписанный локальный сертификат для MAX непригоден.

## Резервные копии

Подготовленная команда для Linux-сервера; запускается ежедневно администратором/таймером после размещения:

```sh
umask 077
mkdir -p backups
docker compose --env-file .env.production -f compose.production.yaml exec -T db pg_dump -U navigator -d navigator -Fc > "backups/navigator-$(date +%F-%H%M).dump"
```

Копии хранить за пределами VPS с ограниченным доступом. Не отправлять их в публичный репозиторий. Восстановление сначала проверять в отдельной БД. План хранения/удаления, расписание, внешнее хранилище и фактическое восстановление ещё не настроены и не проверены.
